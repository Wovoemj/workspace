# 第4章 系统设计

系统设计是将需求分析转化为技术方案的过程。本章从总体架构设计、功能模块设计、接口设计三个方面，阐述智能旅游助手系统的技术方案。

## 4.1 总体架构设计

系统采用前后端分离的分层架构，将系统划分为四个层次：客户端层、网关层、应用层、数据层。这种分层设计使得各层职责清晰，便于独立开发、测试和维护。

### 4.1.2 架构说明

**客户端层**：负责用户界面展示和交互。用户前端采用Next.js 14框架，提供服务端渲染能力，有利于SEO和首屏加载。管理后台采用React + Vite框架，提供高效的管理界面。

**网关层**：负责请求路由、静态资源服务、负载均衡。开发阶段使用Next.js的Rewrites功能将API请求转发到Flask后端，生产环境可使用Nginx作为反向代理。

**应用层**：负责业务逻辑处理。Flask主服务处理用户管理、景点管理、订单管理等核心业务。Go AI服务专门处理大语言模型调用，利用Go的高并发特性处理流式响应。

**数据层**：负责数据存储和缓存。SQLite/MySQL存储持久化数据，Redis存储缓存数据和会话信息。当Redis不可用时，系统自动降级为内存缓存。

## 4.2 功能模块设计

根据需求分析，系统划分为以下功能模块，每个模块具有明确的职责和接口。

### 4.2.1 用户管理模块

**职责**：处理用户注册、登录、个人信息管理、会员体系等功能。

**核心组件**：
- 用户模型（User）：存储用户基本信息
- 认证服务：JWT令牌生成和验证
- 密码加密：PBKDF2算法加密存储

**接口列表**：
- POST /api/auth/register - 用户注册
- POST /api/auth/login - 用户登录
- GET /api/user/profile - 获取用户信息
- PUT /api/user/profile - 更新用户信息
- PUT /api/user/password - 修改密码

### 4.2.2 景点管理模块

**职责**：管理景点信息，提供景点查询、搜索、筛选功能。

**核心组件**：
- 景点模型（Destination）：存储景点基本信息
- 景点服务：处理景点CRUD操作
- 搜索服务：提供景点搜索功能

**接口列表**：
- GET /api/destinations - 获取景点列表
- GET /api/destinations/:id - 获取景点详情
- GET /api/destinations/search - 搜索景点
- POST /api/destinations/:id/favorite - 收藏景点
- GET /api/destinations/:id/comments - 获取景点评论
- POST /api/destinations/:id/comments - 发表评论

### 4.2.3 产品管理模块

**职责**：管理旅游产品（门票、酒店、机票、体验），提供产品查询和预订功能。

**核心组件**：
- 产品模型（Product）：存储产品信息
- 产品服务：处理产品CRUD操作
- 库存服务：管理产品库存

**接口列表**：
- GET /api/products - 获取产品列表
- GET /api/products/:id - 获取产品详情
- GET /api/products/search - 搜索产品
- GET /api/products/categories - 获取产品分类

### 4.2.4 行程规划模块

**职责**：帮助用户创建、编辑、管理旅行行程。

**核心组件**：
- 行程模型（Trip）：存储行程基本信息
- 行程项模型（TripItem）：存储行程每日安排
- 行程服务：处理行程CRUD操作

**接口列表**：
- GET /api/trips - 获取用户行程列表
- POST /api/trips - 创建新行程
- GET /api/trips/:id - 获取行程详情
- PUT /api/trips/:id - 更新行程信息
- DELETE /api/trips/:id - 删除行程
- POST /api/trips/:id/items - 添加行程项
- PUT /api/trips/:id/items/:itemId - 更新行程项
- DELETE /api/trips/:id/items/:itemId - 删除行程项

### 4.2.5 AI对话模块

**职责**：提供智能问答服务，支持多轮对话、意图识别、行程生成等功能。

**核心组件**：
- 对话服务：管理对话上下文和历史
- 意图识别器：识别用户意图类型
- 大模型客户端：调用MiMo大语言模型API
- 流式处理器：处理流式响应

**接口列表**：
- POST /api/agent/chat - 发送对话消息（流式响应）
- GET /api/agent/sessions - 获取对话会话列表
- GET /api/agent/sessions/:id - 获取会话历史
- DELETE /api/agent/sessions/:id - 删除会话

### 4.2.6 订单管理模块

**职责**：处理产品预订、支付、订单查询、退款等流程。

**核心组件**：
- 订单模型（Order）：存储订单信息
- 订单项模型（OrderItem）：存储订单产品明细
- 购物车服务：管理用户购物车
- 订单服务：处理订单生命周期

**接口列表**：
- GET /api/cart - 获取购物车
- POST /api/cart - 添加产品到购物车
- PUT /api/cart/:id - 更新购物车产品数量
- DELETE /api/cart/:id - 删除购物车产品
- POST /api/orders - 创建订单
- GET /api/orders - 获取订单列表
- GET /api/orders/:id - 获取订单详情
- POST /api/orders/:id/pay - 支付订单
- POST /api/orders/:id/cancel - 取消订单

### 4.2.7 系统管理模块

**职责**：提供管理后台功能，管理景点、产品、订单、用户等数据。

**核心组件**：
- 管理服务：处理管理员操作
- 数据统计服务：生成运营数据报表
- 配置服务：管理系统配置参数

**接口列表**：
- GET /api/admin/dashboard - 获取仪表盘数据
- GET /api/admin/destinations - 管理景点列表
- POST /api/admin/destinations - 添加景点
- PUT /api/admin/destinations/:id - 编辑景点
- DELETE /api/admin/destinations/:id - 删除景点
- GET /api/admin/orders - 管理订单列表
- PUT /api/admin/orders/:id/status - 更新订单状态
- GET /api/admin/users - 管理用户列表

## 4.3 接口设计规范

系统采用RESTful API设计风格，遵循以下规范：

### 4.3.1 URL命名规范

- 使用名词复数形式表示资源集合：`/api/destinations`、`/api/products`
- 使用ID标识具体资源：`/api/destinations/123`
- 使用嵌套表示关联资源：`/api/destinations/123/comments`

### 4.3.2 HTTP方法规范

- GET：获取资源，不产生副作用
- POST：创建新资源
- PUT：更新已有资源
- DELETE：删除资源

### 4.3.3 请求响应格式

**请求格式**：
- 请求头：Content-Type: application/json
- 请求体：JSON格式数据

**响应格式**：
```json
{
  "code": 200,
  "message": "success",
  "data": { ... }
}
```

**错误响应**：
```json
{
  "code": 400,
  "message": "参数错误",
  "error": "具体错误信息"
}
```

### 4.3.4 身份验证

采用JWT（JSON Web Token）身份验证机制：
1. 用户登录成功后，服务器生成JWT令牌返回给客户端
2. 客户端在后续请求中，在请求头中携带令牌：`Authorization: Bearer <token>`
3. 服务器验证令牌的有效性，提取用户信息

### 4.3.5 分页查询

列表接口支持分页查询，参数包括：
- page：页码，默认1
- per_page：每页数量，默认20
- sort：排序字段
- order：排序方式（asc/desc）

响应包含分页信息：
```json
{
  "data": [...],
  "pagination": {
    "page": 1,
    "per_page": 20,
    "total": 100,
    "pages": 5
  }
}
```
